# AI 云药师——微信小程序开发计划

## 一、文档说明

本计划基于已完成的 PRD（`07-competition/product-plan.md`）、线框图（`06-prototype/wireframes/`）、Prompt 与护栏（`03-prompts/`）、验证结论（`04-verification/`），描述如何把它们实现为一个可运行的微信小程序 MVP。

前 7 个阶段已经把「产品是什么、AI 怎么做、页面长什么样」定义清楚，本阶段解决「怎么把代码写出来」。

---

## 二、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生小程序（WXML / WXSS / JS） | 只做微信端，原生最快、无框架负担 |
| 后端 | 微信云开发（云函数 + 云数据库 + 定时触发器） | 免服务器运维，快速上线，免费额度够 MVP |
| AI 文案 | 大模型 API（云函数内调用） | 生成 80 字暖心文案 |
| 护栏 | 云函数内规则引擎 | G1-G6 硬阻断 + 软修正，毫秒级 |
| TTS | 讯飞语音合成 | 中文药名准确率高 |
| 短信 | 腾讯云 SMS | 断档/漏服兜底触达 |

## 五、关键技术难点与方案

### 难点 1：订阅消息机制（能否成立的关键）

**现实约束**：本项目是**个人主体**注册，拿不到「长期订阅」模板（长期订阅需企业主体 + 医疗类目 + 资质），只能用「一次性订阅」。

**一次性订阅的核心解法：续订闭环**

一次性订阅「授权一次只能发一条」，单靠它发提醒会断。解法是把续订点放在老人**必然的操作**上——点「已吃药」：

```
老人收到提醒（消耗上一次攒的额度）
   ↓ 点「已吃药」
同时调起 requestSubscribeMessage
   ↓ 老人点「允许」
为下一次提醒续上额度
   ↓
下一次提醒发出（消耗这次续的额度）
   ↓ ……循环
```

**两个关键点**：
1. `requestSubscribeMessage` 必须在用户点击行为里触发，「点已吃药」正好是点击，技术合规。
2. 老人不用额外操作——本来就要点「已吃药」，只是顺手多点一次「允许」。

**边界情况：漏服断档**

老人漏服、没点「已吃药」→ 额度没续上 → 下一次提醒发不出。兜底：
- 短信顶上（L3），保证不漏提醒
- 老人下次点开小程序 / 点订阅卡片时，再引导重新订阅

**长期订阅留给未来**：商业化上线时补企业主体 → 医疗类目 → 长期订阅，代码里预留接口，届时直接切换。

### 难点 2：定时调度

- 小程序不能常驻后台，提醒靠**云函数定时触发器**（cron）到点执行。
- 应对：MVP 用「每 5 分钟扫一次待发计划」的触发器，简单可靠；后期优化为精确 cron。

### 难点 3：AI 护栏的实时性

- LLM 生成文案有延迟（1-3 秒），护栏必须在返回前拦截。
- 应对：护栏用规则引擎（关键词 + 正则），毫秒级，不额外调 LLM。

### 难点 4：语音录药（二期）

- 老人自助录药需语音输入 + AI 解析，MVP 先不做，走「子女代录」。
- 二期用微信原生语音转文字 + AI 拆解字段。
